# 账号、渠道与调度优先级

适用版本：**1.0.9**。

## 设置优先级

在面板 **账号池与运维** 选择国内或国际区域。在账号行的“调度优先级”输入非负整数，点击“保存优先级”。

| 状态 | 含义 |
| --- | --- |
| 名称旁“优先级 100” | 当前已保存的值 |
| 未保存 | 输入框中存在草稿，调度继续使用已保存值 |
| 保存中 | 正在提交到服务端 |
| 已保存 · 重启保留 | 服务端已写入账号 JSON |
| 保存失败提示 | 保留草稿，可再次点击保存 |

默认优先级为 `100`，取值范围 `0–2147483647`，数字越小越早调用。保存成功后账号表按启用状态、优先级排序。定时刷新保留未提交草稿；账号名称旁的徽章始终显示已保存值。

## 持久化

优先级保存为账号 JSON 的 `priority` 字段。API 响应、账号导出包含该字段；重启重新载入。旧账号缺少该字段时默认 `100`。

凭证刷新保留优先级。重新 OAuth 登录或覆盖导入同一账号时，若新的凭据没有提供 `priority`，保留原值；若导入内容明确提供合法优先级，使用该值。保存失败会恢复原调度值。

Docker 部署需要持续挂载 `/app/accounts`。更换挂载目录会加载另一套账号和设置；部署步骤见[部署说明](integration-plan.md)。

## 调度顺序

1. 请求根据 Key 绑定或默认出口选择国内／国际账号池。
2. 账号池从最小优先级开始，结合停用、冷却、在途限制、模型限制、保留积分和每日限额判断候选账号。
3. 该优先级没有可用账号时，尝试下一个优先级。
4. 同优先级内，免费模型优先选择当天免费 Token 总量最少的账号；付费模型优先选择当天实际积分消耗最少的账号。

例如 A、B 的优先级为 `10`，C 为 `100`：先在 A、B 中按用量选取；两者都不可用时再使用 C。若 A 为 `0`，它可用时会比 B、C 更早选取。长期只使用最小优先级是该设置的预期效果。

## 按用量均衡

| 请求类型 | 主要比较值 | 用量相同时 |
| --- | --- | --- |
| 免费模型 | 账号当天全部免费模型的 `total_tokens` 总和 | 优先在途请求少的账号，再轮询 |
| 付费模型 | 账号当天实际消耗的积分总和 | 开启加权选号时按剩余积分与闲置补偿抽取；关闭时轮询 |

免费计量合并全部免费模型，例如 A 今天用了 20K、B 用了 80K、C 用了 120K 免费 Token，会先让 A 承接请求，逐步接近其他账号。不同请求的长度会造成短暂差距，完成后按实际用量继续调整。付费请求的 Token 不增加免费负载；免费请求不以剩余积分多少决定均衡顺序。

付费均衡使用上游返回的实际积分，而非 Token 数量、请求次数或人民币成本估算。已有会话绑定只有在该账号仍属于同优先级内积分消耗最少的可用账号时才复用，否则重新分配。免费请求跳过会话绑定，避免长会话集中占用一个账号。

计量每天在服务的本地零点重置，重启从 `usage.jsonl` 和保留的归档恢复当天用量。每日限额为 `0` 时仍持续计量。新请求记录保留 `billing_mode`；实际积分为零判为免费，正数判为付费，无积分字段时依据所属渠道的模型目录判断。旧日志缺少标记时按同样规则回填；不虚构未报告的积分。沿用用量统计规则：客户端取消不参与计量，有已报告用量的上游失败保留实际消耗。

账号页在 Token 列显示“今日免费”，在积分列显示“今日消费”；管理 API 的账号视图包含 `freeTokensToday` 和 `dailyCreditsToday`。这些是调度的当日计量，Token 自动使用 K/M/B 显示，API 保留整数。

`pool.free_fair_pick` 默认开启，关闭后免费请求使用原有选号和会话规则。停用、冷却、在途上限、限额、保留积分及积分地板仍参与候选过滤。国内与国际池分别均衡，账号优先级无法跨 Key 的固定渠道，也不会为了均衡而越过更小优先级的可用账号。

## 管理 API

修改账号的入口为 `POST /accounts/set`，需要面板会话及原有管理鉴权。请求示例：

```json
{"uid": "account-uid", "priority": 10}
```

成功返回 `{"account": {..., "priority": 10}}`。非法值返回 `400`；账号不存在返回 `404`。该入口也保留 `enabled`、`proxy` 和 `proxySlot` 的独立更新功能。客户端余额与用量查询使用 API Key，见 [API 说明](api.md)。
